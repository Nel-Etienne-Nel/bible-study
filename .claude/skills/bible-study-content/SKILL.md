# Adding content to the Bible Study site

The site has two ways in: **Books** (the text, and every teaching on it) and
**Teachers** (their series, broken into lessons). Everything is generated by
`build.js` from data files, so adding content means editing data and nothing
else. Read `README.md` if you need the file formats in full.

```
data/books.js                        which books appear, in canonical order
data/scripture/<book>.js             the text — generated, never edit by hand
data/teachers/<teacher>.js           a teacher, their bio and series list
data/studies/<teacher>/<series>.js   a series: SECTIONS (lessons) + NOTES
```

## Pick the job

| The user… | Read |
|---|---|
| pastes a transcript, or says "ep N" / "next episode" | `references/transcript.md` |
| wants a new book of the Bible on the site | `references/new-book.md` |
| wants a new teacher, or a teacher's series on another book | `references/new-teacher.md` |
| wants a note, highlight or range changed | the relevant section of `references/transcript.md`, then publish |

A transcript for a teacher or book that isn't on the site yet needs the
book and teacher added first — do those, then the transcript.

## Two tools you'll use every time

```sh
node tools/verses.js song-of-solomon 5:2 5:9   # the passage exactly as the site has it
node tools/check_study.js                       # verify every lesson and note against the text
```

`verses.js` prints one poetic line per row. Write highlight phrases from
this output, not from memory or the teacher's quotation — the site uses the
World English Bible and teachers often quote another translation, so their
wording will not match.

`check_study.js` catches what would otherwise fail silently on the page: a
phrase that highlights nothing, a note on a verse that doesn't exist, two
lessons starting on the same verse. Errors must be zero. Read the warnings —
they are judgement calls, not failures.

## Publishing

Once the content is in:

1. `node tools/check_study.js` — zero errors.
2. `node build.js` — it stops with a plain message if data doesn't line up.
3. Look at what you changed. Serve it and open the new lesson page:
   `python3 -m http.server -d dist 8000`. If you can drive a browser, check
   the notes sit beside their verses and nothing errors in the console.
4. Commit and push to `main`:

   ```sh
   git -c user.name="Nel-Etienne-Nel" -c user.email="neletienne18@gmail.com" commit -m "…"
   git push origin main
   ```

   Commit as the site's owner, with **no** `Co-Authored-By` or
   `Claude-Session` trailers — the owner asked for commits without AI
   attribution, and that instruction outranks default attribution guidance.

   The message should say what was added, and — if a lesson's range moved —
   what in the transcript showed the old range was wrong.

Pushing to `main` is the deploy: Cloudflare builds the Worker `bible-study`
with `node build.js` and publishes it with `npx wrangler deploy`. Never
commit `dist/` or `pdf/`.

## Reporting back

Tell the user, briefly:

- the lesson's range, and whether it confirmed or corrected what was there
- a table of verse → note title
- anything you chose not to do or softened, and why, so they can overrule it
- anything the transcript left ambiguous

Sessions run in fresh containers. If the repo isn't checked out, clone it
first; Node is needed for every job, Python only for adding a book.
